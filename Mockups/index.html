Libra Asset Search — UI design options

Clickable prototypes for evaluation. Nothing here is wired to the running app.

Two directions are built out below. Both are static HTML with no build step and no network calls — open them, click around, and use the Design notes button in the top right of each to see exactly what changed and what it would cost to build.

Asset IDs, names, entity types, collections and qualified names are real, sampled from Chatbot/main_assets.csv. Owner and expert values are illustrative — those columns exist in the real file but are empty on all 904 rows. Table previews are representative placeholders. Both prototypes reuse the brand tokens from app/client/styles.css, so what you are judging is layout and interaction, not colour.

They compose

B and C are not either/or. A workbench with a synthesised answer sitting above the result list is the Glean model, and neither forecloses a full conversational UI later. B first — it needs no backend change, so it is reversible. C second, once there is a chat deployment on hokieopenai; today that account has only text-embedding-3-large.

What both prototypes are fixing

Preview loses your work
#/view, #/table and #/image take over the entire window in a new tab. You abandon your results to look at one file.
No way to narrow
15 results arrive with assetEntityType on every one of them, and it does nothing beyond a grey pill.
The best content is hidden
userDescription is a full AI-written document per asset. Only a one-line extractive caption ever reaches the screen.
Relevance is meaningless
relevance 2.43 on an unlabelled 0–4 reranker scale tells a user nothing.
Rating comes too early
RatingBar renders above the results, asking for a verdict before anything is on screen.
Cards are type-blind
A PDF, a Cosmos container and a Databricks table render identically.
Nothing is shareable
The query never reaches the URL, so a search cannot be bookmarked or sent to a colleague.
Zero results is a dead end
“Try rephrasing” with no relaxed retry and no suggestions.

The blocker: owner and expert are empty on every row, so all Stewardship facets read “No owner: 904”. The values are in Reporting/csv_exports/main_assets.csv as contact_owner_id / contact_expert_id — 4 assets have an owner, 5 have an expert, across just 4 distinct Entra object IDs. Resolve those four through Graph and hardcode the map.

Correction to earlier advice: you do not need owner_count / expert_count columns. That guidance assumed delimited multi-value strings. With plain scalars, owner eq '' is directly filterable in Azure AI Search, so the two columns you have are sufficient.

Worth a decision: asset_type_friendly collapses five Databricks/Hive entity types into one “Databricks” bucket, so a user cannot separate a view from a table. The prototype keeps asset_entity_type as a second, finer facet alongside it — costs nothing and restores the distinction.

Deferred by choice

Classifications and managed attributes are not in the file and not on the screen. When you want them, only two are safe at asset grain — the rest fan the 904-row grain out:

DimensionGrainVerdict
DataClassification.DataClassification1:1 · 90 assetsSafe. The best governance facet available.
classification_source1:1 · 19 assetsSafe. DataScan vs PurviewPortal.
tag11 of 11 assets multi · max 3Every tagged asset has more than one.
DataClassification.DocumentLevel2 of 10 multi · max 4One asset holds Internal, Confidential and Restricted.
classification_typename4 of 76 multi · max 2e.g. DCAT1 + MICROSOFT.POWERBI.ENDORSEMENT.
contact_expert_id1 of 5 multi · max 2NFLPlayByPlayData has two. Decide first-value vs collection field.

Why not just semicolon-join the 1:N ones? Because "DCAT1; MICROSOFT.POWERBI.ENDORSEMENT" is a single facet value, not two. You get one bucket per combination, facet counts stop summing to the result total, and a user cannot tell whether a filter means “has this” or “has exactly this set”. Model them as Collection(Edm.String) in the index instead.

Index side, when you are ready: add fields as filterable + facetable in scripts/create-index.ps1, and map them in both places in scripts/ingest.ps1 — the $prepared object and the Flush-EmbedBatch hashtable. Miss one and the column drops silently. Adding new fields is additive; changing an existing field (making collectionId facetable) forces a full rebuild, so add collectionName as a new field instead.

How to evaluate

Try these in Option B

  1. Filter Stewardship → No owner or expert.Purview cannot do this. Is a remediation worklist worth populating the columns?
  2. Then hit Export.Scope, columns, real CSV. Is this the hand-off your stewards need?
  3. Compare Platform against Entity type.asset_type_friendly merges Hive views into Databricks. Do you need both facets?
  4. Select staff_table, open Stewardship then Locations.Right amount of metadata, or too much?
  5. Sort by Least governed first.Useful default for a stewardship review?
  6. Search xyzzy.Is the relaxed retry the right recovery?

Try these in Option C

  1. Watch the answer stream.Does the wait feel shorter than a spinner would?
  2. Hover a citation.Is the link between claim and source convincing enough to trust?
  3. Open the retrieval trace.Is this a governance asset or noise for your audience?
  4. Read the grounding footer.Descriptions, not data. Is that distinction clear enough?
  5. Ask xyzzy.Refusing beats inventing — but is the wording right?
  6. Click a follow-up.Is this enough multi-turn value to avoid building full chat?

One decision to make before any build

Design system

The app hand-rolls ~460 lines of CSS today, and both prototypes continue that. Worth settling before committing, because it is expensive to reverse:

  • Keep hand-rolled CSS — smallest bundle, total control, accessibility is on you.
  • Fluent UI v9 — reads as first-party Microsoft, which suits a Purview accelerator, and gives accessible components free. Costs bundle size and some of the current lightness.
  • Radix + Tailwind — maximum control with accessible primitives; a larger authoring shift.
  • Mantine — fastest to a polished result, least distinctive.
